# 出欠システムを自前バックエンドへ載せ替える（計画）

作成 2026-08-19。**まだ着手していない。** 実装前にこの文書を読み直すこと。

---

## なぜ変えるのか

GAS版の主催者セットアップが重すぎる。実測でこれだけの段がある。

1. テンプレートの表をコピー
2. 拡張機能 → Apps Script
3. デプロイ → 新しいデプロイ → 種類の選択 → ウェブアプリ
4. 承認（「このアプリはGoogleで確認されていません」→ 詳細 → 安全ではないページに移動 → 許可）
5. 出てきたURLをコピーしてセットアップ画面に貼る

3〜4は**スマホでは実質できない**。Apps Script のエディタもデプロイのダイアログもモバイルでは操作にならない。
「安全ではないページ」で引き返す人も実際にいた。

さらに重いのは初期設定より**日常の操作**のほう。
**Googleスプレッドシートのスマホアプリはアドオンのサイドバーを動かさない。**
つまり行事を取り込むたび・出欠を作るたびに、主催者はPCかデスクトップ表示のブラウザを開くことになる。
主催者の操作画面が表の中にある限り、この制約は外れない。

## 決めたこと（2026-08-19）

| 論点 | 結論 |
|---|---|
| 他団体の個人情報を預かるか | **預かる。** BYOBをやめる |
| 想定規模 | 十数〜数十団体 |
| 現行GAS版 | **新版に置き換える**（併存させない） |
| 技術選定 | **Cloudflare Workers + D1** |
| ドメイン | `dropper-tools.com` は Cloudflare で取得ずみ。`api.dropper-tools.com` をそのまま生やせる |

### なぜ Firebase でも Supabase でもないのか

- **Supabase は外れる。** 無料プロジェクトは一定期間アクセスがないと休止する。
  月に数回しか開かないクラブの出欠とは致命的に相性が悪い（大会前に開いたら止まっている）
- **Firebase は Cloud Functions が Blaze（カード登録）必須。**
  回避するにはブラウザから Firestore を直接叩き、セキュリティルールだけで参加者の書き込みを守ることになる。
  できるが繊細で、荒らし対策も打ちにくい
- **Workers はカード登録なしの無料枠が広く、D1 は休止しない。**
  出欠のサーバー処理は「回答を1行足す・名簿を返す・集計する」だけで、Workers の形にそのまま合う。
  主催者のログインは Google Sign-In のIDトークンを Worker 側で検証すれば足り、Firebase を挟む必要がない

> 無料枠の条件は変わる。**着手前に現時点の内容を必ず確認すること。**
> カード登録なしで始められることもあわせて確認する。

## 構成

| | 中身 |
|---|---|
| 画面 | いまの `attend/`（GitHub Pages・`app.dropper-tools.com`）をそのまま使う |
| API | Cloudflare Worker（`api.dropper-tools.com`） |
| データ | D1（SQLite） |
| 主催者の認証 | Google Sign-In。IDトークンを Worker 側で検証 |
| 参加者 | **ログインなし・アプリなし**（今と同じ） |

画面は GitHub Pages、APIは Worker で**別オリジン**になる。CORS が要るが、
Worker は自分でヘッダーを返せるので、GAS のときのような
「404ページにCORSヘッダーが無くてブラウザがCORSと報告する」事故は起きない。

### 主催者の新しい手順

1. 周知サイトの「使ってみる」
2. Googleでログイン（見慣れた同意画面。「安全ではないページ」は出ない）
3. 団体名を入れる
4. 名簿を入れる
5. できあがり。配るURLが3本出る

**全部スマホで完結する。** デプロイ・承認画面・書き込みキー・テンプレートのコピーが全部消える。
そのあとの行事の取り込みも出欠の作成も普通のブラウザで動くので、サイドバー問題ごと無くなる。

### URLの扱い

いまの形 `…/attend/?s={デプロイID}` の **`s` の中身が団体IDに変わるだけ**。URLの形は変えない。
リッチメニューの差し替えは白山クラブの1回で済む。

団体IDは**推測できない長さのランダム**にする。IDを知っていれば名簿の氏名が見えるのは今と同じだが
（GAS版もデプロイIDを知れば見えた）、置き場が開発者側になるぶん、IDの強度は今より重要になる。

## データ設計

いまのシート構成をほぼそのまま持ち込む。

- `orgs` … 団体名、持ち主のGoogleアカウント、作成日時、最終アクセス
- `members` … 氏名、性別、並び順
- `taikai` … 行事。読み取った要項の置き場。出欠イベントIDを持つ（空＝未使用）
- `events` … 出欠を受け付けている行事
- `answers` … **追記式のまま。集計は latest-row-wins**

回答を上書きしない方針、端末UUIDでの記憶、男女別集計、未回答者は主催者にだけ見せる。
**この挙動は変えない。** 移行後に「前と違う」と言われる箇所を作らないため。

## 段階

| # | 内容 |
|---|---|
| 1 | Worker＋D1の土台、主催者ログイン、団体作成、名簿 |
| 2 | 参加者の画面（一覧・回答・わたしの回答・みんなの回答）を新APIへ |
| 3 | 行事（貼り付け取り込み・一覧・出欠を作る）。**ドロッパー側は無変更** |
| 4 | 白山クラブのデータ移送、リッチメニューのURL差し替え |
| 5 | GAS版とテンプレート配布の停止、周知サイトと規約の書き換え |

ドロッパーが段階3で無変更なのは、受け渡しが「クリップボードに載せるだけ」になっているから。
貼り付け先が表のサイドバーからWebページに変わるだけで、`saveToken` の形は触らない。
**符号化を変えるときは取り込み側と両方そろえる**（GAS版と同じ約束）。

## 先に潰しておく問題

### LINEの内蔵ブラウザではGoogleログインが弾かれる

Googleは埋め込みWebViewからのOAuthを拒否する。主催者は「外部ブラウザで開く」必要がある。
**参加者はログイン不要なので影響しない。** いまの承認画面より軽い障害だが、ゼロではないので
画面に先回りして書く。

### 削除の受け口を最初から作る

「この団体をすべて削除」を主催者自身が押せるようにする。削除請求のたびに手作業をしないため。
数十団体だと、これが有るか無いかで運用負荷がまるで違う。
最終アクセスから一定期間で自動削除する仕組みも**初回に入れる**。あとから足すのは面倒。

### 規約と公約の書き換え（段階5）

「サーバーを持たず、あなたのデータを預かりません」は**シリーズ全体の公約**として複数箇所にある。

- `dropper/src/i18n/*.json` の `privacy.s2body`「当方はサーバーを保有していません」
- `guide.s1body2` / `gdecide.s1body2`「ドロッパーはサーバーを持たず、あなたのデータを預かりません」（太字）
- `tool4.desc`「回答はあなた自身のGoogleスプレッドシートにだけ保存されます」／`tool4.tag3`「データは自分の表の中だけ」
- 配布ずみの表の「はじめに」シート「出欠のデータはあなたのGoogleドライブから外に出ませんし、作った人にも渡りません」

**出欠だけが例外であることを明記する**書き方にする。他の3本は今までどおりブラウザ完結なので、
まるごと撤回する必要はない。`privacy.s11line3` を見ると、LINE版では既に運営者のAPIキーを使っているので、
「サーバーを持たない」には元から例外がある。ゼロからの方針転換ではない。

必要になるもの: 保管場所、保存期間、削除方法、問い合わせ先、Cloudflareを使うことによる越境移転の説明。

**配布ずみの表の文言は自動では直らない**（`初期設定` が書いた文なので既存コピーには反映されない）。

### 費用

Workers と D1 の無料枠は、数十団体の出欠には桁が2つほど余る。ただし前述のとおり着手前に確認する。

## 移行

白山クラブのデータ（名簿・イベント・回答）は件数が小さいので、GAS側に書き出し関数を1つ足して流し込む。

**移行が済むまで現行GAS版は止めない。** 新版で問題が出たら戻れる状態を保つ。

配布ずみのテンプレートは、いまのところ白山クラブとテスト用のコピーだけなので影響は限定的。

---

## 失うもの

正直に記録しておく。

- **「データは自分の表の中だけ」という、いちばん強い売り文句を失う**
- 出欠を集めた結果を主催者が自分のスプレッドシートで自由に加工できる利点も無くなる

後から「主催者がボタンを押すと自分のGoogleスプレッドシートに書き出す」機能で部分的に取り戻せる。
初回には入れないが、**設計上そこへ伸ばせる形にしておく。**

## 検討して採らなかった案

| 案 | 採らない理由 |
|---|---|
| ブラウザ完結（サーバーなし） | 出欠は「別々の端末・別々の時刻に書き込み、全員が同じものを見る」データ。置き場が無いので成立しない |
| Googleフォーム | 行事ごとに別URLになり、リッチメニューに貼った3本のURLで回す形が壊れる。端末記憶・回答の上書き・男女別集計も作り直しになる |
| Apps Script API でデプロイを自動化 | 利用者ごとに開発者向け設定でAPIアクセスを許可させる手間が増え、`script.deployments` の追加は承認済みスコープの再審査を招く |
| BYOBのまま主催者UIだけWebへ出す | 初期設定のPC必須（デプロイ）が残る。書き込みキーを主催者の端末に覚えさせる必要も戻る。**「預かってよい」と決まったので不要になった** |
| 主催者ごとに自分でBaaSを契約 | セットアップがGASより重くなる |
